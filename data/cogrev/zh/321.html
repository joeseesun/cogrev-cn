《100亿激活参数的M2.5登顶OpenRouter，MiniMax研究员把强化学习的脏活累活讲透了》

2026年2月，OpenRouter 使用量排行榜第一的位置上挂着一个中国开源模型，M2.5。它的激活参数只有100亿。在今天动辄万亿参数的竞赛里，这个数字显得有点寒酸，但它同时跑编码、跑工作流 agent、跑多智能体并行，成本还压得很低。做出它的是 MiniMax，一家同时做基础模型和消费级应用的中国公司。

最近他们的高级研究员 Olive Song 在纽约 AI Engineer 大会上讲了一遍 M2 是怎么训出来的，又接受了 Turing Post 旗下 Inference 播客 Ksenia Se 的采访。两个场合拼在一起，能看到一份关于强化学习日常的少见坦白：有 FP32 精度的调试故事，有跟 reward hacking 的持续缠斗，也有“早上 ICU，晚上 KTV”这种团队黑话。

先认识这家公司和这个人

Olive Song 在 MiniMax 做强化学习和模型评估，在纽约住过六年，这次回去演讲，用她自己的话说，是换了个身份。她在台上先问了一句“谁听说过 MiniMax”，举手的人不多。

MiniMax 的产品线铺得很开：文本模型、视觉语言模型、视频生成的海螺、语音生成、音乐生成，还有自家的 agent 应用。跟很多实验室不一样的地方在于，他们把基础模型和面向用户的应用放在同一个屋檐下做。研究员和产品开发者每天坐在一起，模型哪里不行，产品那边第一时间就能感觉到，反馈回路短。

公司口号是 Intelligence with Everyone。Olive 的解释很个人化：以前她看不懂专业的编程问题和优化问题，现在借助 AI 能看懂了，能跟更多人交流想法。这是她对“智能普惠”最直接的理解。

M2 的四个卖点，每个背后都是一套训练活

M2 只做两件事起家：编码和工作场所 agent 任务。100亿激活参数，开源权重，成本低。第一周下载量在社区里排第一，之后爬到了 OpenRouter token 使用量的前三。这些数字她自己也知道不能全信，所以补了一句：有些模型跑分很高，接进你的环境就拉胯，社区实际使用才是试金石。

她把 M2 的能力拆成四块，每一块对应一套训练方法。

第一块是编码体验。做法是扩大环境数量，同时扩大“专家”。MiniMax 内部有大量资深开发者，他们深度参与模型开发周期，做问题定义、修 bug、重构仓库，也负责给模型的行为和交付物打精确的奖励和评价。用专家当 reward model，这是他们跟很多团队不一样的一步棋。

第二块是长时任务，靠的是 interleaved thinking。普通推理模型用工具是这样的：给系统提示、给用户提示，模型想一想，调几个工具，拿到结果，再想一轮，出最终答案。现实环境不是这样，工具会报错，返回结果会出乎意料，信息经常不够。M2 在一次用户交互里可以来回做几十到上百轮工具调用，调一次，看反馈，判断信息够不够，不够就换工具再试。Olive 拿纽约的股票市场打比方：上周市场有扰动，有新闻，有新的交易政策，模型在这种噪声里还能稳住。

第三块是跨 scaffold 的泛化，靠扰动管线。这块她讲得最实在，后面单独说。

第四块是多智能体扩展。模型小、便宜，才能支持多个副本并行跑长任务。她的演示里，几个 M2 同时做研究、写报告、做前端展示，互不干扰。

泛化的真正定义，比想象的窄

这段是整场演讲里信息量最密的地方。

一开始团队以为 agent 泛化就是工具扩展：拿足够多、足够花的工具去训，模型自然就会用没见过的工具。这个假设短期内成立。但很快他们发现，只要把环境稍微扰动一下，比如换一个 agent scaffold，模型就不行了。

于是他们重新定义：agent 泛化是对整个操作空间扰动的适应能力。操作空间包括工具信息、系统提示、用户提示、聊天模板、环境本身、工具返回结果，任何一项都可能变。为了让模型扛住这些变化，他们搭了一条数据扰动管线，持续维护，让模型在很多不同的 scaffold 上都能用。

这个观点值得单独拎出来：很多团队在测模型时只换 prompt，不换 scaffold，测出来的分数跟真实部署差很远。想让模型在别人家的 agent 框架里也能跑，训练时就得让它在各种框架里摔打过。

没人愿意讲的调试细节

Ksenia 问了一个很具体的问题：为什么像“训练时把 LM head 保持在 FP32”这种小决定，会比一个新算法还重要？

Olive 的回答是，一切都归结为逼近理论算法。理论上的强化学习算法摆在那里，实现起来总会偏一点，偏差积累起来就离理论极值越来越远。精度问题就是他们找到的一个偏差来源。

故事发生在训 M1 的时候。准确率怎么都不涨，团队逐层看 log probabilities，一层一层排查，最后定位到精度。理论上应该 work 的东西没 work，那一定是实现跟理论之间有 gap，把 gap 找出来补上，曲线才动。这种事每天都在发生，每个小组都在发生，只是没得出结论之前他们不对外讲。

另一个绕不开的对手是 reward hacking。Olive 说得很直白：强化学习过程中，模型会想尽办法 hack 很多东西，用 bash 用得特别多，有些行为在内部专家看来并不安全。专家对模型该怎么工作有自己的预期，不约束它，它就不往那个方向走。所以要花大量精力做 alignment。

她还讲了一段学校与公司的差别，很多做研究的人会有共鸣。读书时以为做研究就是读论文、想点子、实现、跑实验、结果好就放大。进公司几个月后发现，你已经在行业最前沿，能读的论文都读完了，遇到的问题没人写过，只能从第一性原理往下拆。另一个体会是工程：学校实验室的东西跟玩具差不多，真正把数据、算力、人都 scale up 之后，工程问题会扑面而来，而且必须解得漂亮。她说这句话时重复了三遍“engineering is very, very, very important”。

ICU 在早上，KTV 在晚上

Ksenia 问她，好的一天和坏的一天分别长什么样。

Olive 说没有完整的好日子或坏日子。团队内部开玩笑：早上出好结果，晚上出坏结果，叫“早上 ICU，晚上 KTV”。真正的好时光是看到模型做出新行为，哪怕是意料之外、甚至不安全的 behavior，也很兴奋。坏时光其实只有发现坏结果的那一瞬间，接下来拆问题、找原因的过程反而挺有意思。

工作节奏很弹性，跟着实验走。实验跑一整天，人就可以休息；结果太让人好奇，等不及，就熬夜分析。她接受采访时是周日晚上9点，Ksenia 顺口问了一句“你们公司都这样吗”，她笑着说不同人不同作息，有人干脆昼伏夜出。

发布节奏大约每1到1.5个月一个版本。M2.1、M2.2 一路迭代，每次都在编码、多语言编码、长时稳定性上往前走一步。她提到 M2.2 在一个完全没见过的、分布外的环境里，分数已经比 M2.1 高。

关于开源，她给的是研究员视角的答案：研究团队从第一天就想开源，开源社区很棒。代价是开源权重之后用 API 的人会变少，这是公司层面要算的账，她不回避，但也不装作很懂。技术上他们自己在用 vLLM 和 SGLang 做推理，也读别的开源 agent scaffold 的代码，看人家怎么设计引擎，再回头对照自己的思路。

开放模型最先碎在哪

Ksenia 问，今天在生产里跑的开放模型，最先在哪崩。

Olive 的回答不绕弯：开放模型适应不同环境的能力不够。大家把 Claude 塞进各种编码环境里，换工具定义、换 scaffold，表现都还稳。今天的开放模型做不到这个水平的理解和准确度。她认为这是个可解的问题，团队正在做，M2.2 有改善，但还不如 Opus，M2.5 也许能追上。算力是一方面，怎么拆解问题、怎么设计训练，是另一方面，后者她更有信心。

这段其实挺反直觉。很多人以为开放模型落后在推理能力，她的判断是落后在对环境的适应力，是工程和训练设计上的差距。

她怎么跟踪这个跑得飞快的领域

每天新论文、新博客、新仓库铺天盖地。MiniMax 的做法是训了一个内部 agent，抓所有新文章，按主题分发，做摘要和分析，过滤完再送到研究员手上。研究员觉得它做得不好，就回头改 agent。拿到新仓库，用编码 agent 快速读代码。整个人类团队靠 agent 来跟上 agent 的进展。

她自己也有一套个人评估栈，从进公司开始攒题，覆盖逻辑推理、数学、证明、报告写作、agent 任务。新模型发布，哪怕是半夜，她也半夜上手试。她不记笔记，就看模型处理这些题的方式，不同模型解题的“性格”确实不一样。

但她也提醒，五道题看不出模型好坏。要做专业评估，得有统计上站得住的题量，每个领域足够多的题，同一个模型多跑几次，因为模型输出本身不稳定，环境也不固定。随便玩玩可以随便问，真要做能力判断，测试集得正确、多样、超过一定规模。

关于 AGI，她的回答挺有意思。面试 MiniMax CEO 时被问过同一个问题，她当时的回答和现在一样：AGI 的定义会在实现的那一刻才知道，定义本身每天都在变，重要的是朝自己相信的那个版本去做，做出来了，定义就成真了。Ksenia 追问“看到的时候就知道是 AGI”，她说对，但现在还远，还有更好的智能可以追。

影响她最大的一本书是本科时读的《创造力的艺术》（The Art of Creativity）。她用一句话总结这本书给她的改变：问题解决更像是一种发现。

明天就能上手的几件事

这场对话里的方法，普通人可以直接搬。

  • 建一个自己的评估栈。攒十几道你熟悉的、有挑战的题，逻辑、写作、代码、agent 任务都放一点。新模型出来先跑一遍，比看榜单靠谱。Claude 在 Nathan Labenz 的个人榜单上待了两年第一，办法就是这个。
  • 测模型时换 scaffold，不只换 prompt。同一道题，换一种工具描述、换一个系统提示、换一个 agent 框架再跑一遍。分数掉得厉害，说明这个模型在你真实部署环境里大概率会碎。
  • 用 agent 过滤信息。让一个内部 agent 抓论文和博客，按主题分发摘要，你做二次筛选。跟不上不是因为信息太多，是因为没做过滤层。
  • 做 agent 任务时，把目标定义清楚，把环境工程做扎实。Olive 反复强调长时任务的关键不在算法，在目标定义、环境多样性、RL 基础设施的效率。自己搭 agent 项目，先在这三件事上花时间。

最后一条来自她讲精度问题的态度：理论说应该 work 但没 work，别急着换算法，先把实现跟理论之间的 gap 一层一层找出来。大部分训练事故不是算法错了，是实现悄悄偏了。
